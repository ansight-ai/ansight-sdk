# Network conditioning harness

The existing MAUI app (`dotnet/Ansight.TestHarness`, app ID
`ai.ansight.dotnet.maui-harness`) enables `Ansight.Connectivity` and includes a
network probe panel near the top of its home screen. Each probe uses a fresh
in-process HTTP/1.1 connection, has a 20-second timeout and an 8 MiB response
limit, and records outcome, bytes, elapsed time and HTTP status as
`network.probe.completed`. The endpoint URL and payload are not logged.

1. Build/run the MAUI harness on an iOS Simulator or Android Emulator and connect
   it to the locally built Ansight host that includes `device.network`.
2. Start the fixture on the Mac's LAN address from this directory (replace the
   example with the address reported by `ipconfig getifaddr en0`):

   ```sh
   python3 network-fixture.py --host 192.168.1.20
   ```

3. Enter the printed URL in the harness and press **Run network probe**. Confirm
   **Succeeded**. The screen's loopback defaults are useful for a basic transfer
   check, but macOS local capture bypasses loopback traffic. For conditioning,
   both platforms must use the Mac's LAN address. The fixture exposes only
   generated bytes; stop it when testing is finished.
4. Approve mitmproxy's Network Extension in macOS System Settings if requested.
   Use mitmproxy 12.2.3 and the CLI checkout's new host build; no CA trust or device
   proxy configuration is needed.
5. Validate and run the task from `dotnet/Ansight.TestHarness`:

   ```sh
   npx tsc -p ansight/tasks/tsconfig.json
   ansight app register ai.ansight.dotnet.maui-harness --codebase "$PWD" --json
   ansight task list --app-id ai.ansight.dotnet.maui-harness --repository "$PWD" --json
   ansight task run network.conditioning --app-id ai.ansight.dotnet.maui-harness \
     --repository "$PWD" --session-id <connected-session-id> \
     --input '{"endpoint":"http://192.168.1.20:8765/bytes?count=262144"}' --json
   ```

The generated declarations require TypeScript 5.8 or newer. The task verifies
baseline success, success at 256 kbps with delay/jitter, proxy byte counters,
failure under TCP blocking and success after reset. It uses the default 256 KiB
fixture response; the required `endpoint` input must return at least that amount for
the counter assertion. Request failures and applied conditions are separate
capture events from OS connectivity observations.

The task always resets its lease in `finally`, and the host also cleans it up if
Node terminates before `finally` can execute. The hard lease limit is 60 seconds
for this task. Android shaping affects all TCP traffic in the selected emulator;
iOS shaping selects the app PID. Ansight control ports bypass shaping.

This exercises TCP failures without changing radios. It does not test Wi-Fi to
cellular transitions, captive portals, signal strength, OS offline state or
QUIC. Those require a different backend or physical-device testing.

Implementation and API details are in the CLI repository's
`docs/network-conditioning.md`. End-to-end execution requires local-capture
approval; type-checking and building the harness do not prove live PID routing.
Process-scoped routing, throttling, blocking and recovery were verified on macOS
using a LAN-address fixture. The task also checks proxy counters to detect bypass.
The full task passed all six assertions on iOS Simulator with mitmproxy 12.2.3;
Android builds are verified, but its live conditioning task has not yet been run.
